Configurator — локальная система для ведения каталогов компонентов и подбора совместимых сборок. В ней можно описать
любую предметную область, например компьютерные комплектующие, оборудование рабочего места или набор модулей изделия,
а затем задать характеристики и правила совместимости, подобрать состав и сохранить результат.

Система предназначена для одного доверенного пользователя и работает на его компьютере. Основной способ установки —
готовый пакет для Windows или macOS с Docker Desktop. Текущая стабильная версия — `v1.2.0`.

> [!IMPORTANT]
> В приложении пока нет действующей аутентификации и разграничения доступа. Поддерживается только локальная работа
> через `http://127.0.0.1:8080`. Развёртывание в локальной сети, интернете или на общем сервере не поддерживается.

## Как устроена работа

Данные организованы последовательно:

```text
предметная область
  -> типы компонентов
    -> атрибуты
      -> компоненты
        -> связи и правила совместимости
          -> сборка
            -> сохранённая конфигурация
```

Например, в области «Сборка ПК» можно создать типы «Процессор», «Материнская плата» и «Оперативная память», описать
их характеристики, добавить конкретные модели и определить, какие из них совместимы. Конфигуратор будет предлагать
подходящие варианты, показывать причины запрета и проверять связность итоговой сборки.

Для знакомства с системой можно создать готовую демонстрационную область «Сборка ПК». Подробный путь от первого
запуска до сохранения и обслуживания данных описан в [руководстве пользователя](docs/user/USER_GUIDE.md).

## Возможности

| Раздел                       | Что можно сделать                                                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Предметные области           | Создавать пустые и демонстрационные области, изменять их, переключаться между ними и удалять вместе с зависимыми данными              |
| Типы компонентов             | Задавать структуру каталога, порядок и необязательный код типов                                                                       |
| Атрибуты                     | Вести общий каталог характеристик области, подключать один атрибут к нескольким типам и отдельно настраивать обязательность и порядок |
| Компоненты                   | Создавать и изменять записи, искать и фильтровать их, просматривать карточками или таблицей, архивировать и восстанавливать           |
| Изображения                  | Загружать галерею в MinIO, менять порядок, выбирать заглавное изображение и использовать уменьшенные копии в списках                  |
| Ручная совместимость         | Явно связывать пары компонентов и сохранять поясняющий комментарий                                                                    |
| Автоматическая совместимость | Создавать правила сравнения атрибутов, включать и отключать их, получать объяснение результата                                        |
| Граф совместимости           | Просматривать прямые связи и найденные цепочки между компонентами                                                                     |
| Конфигуратор                 | Подбирать компоненты с учётом текущей сборки, заменять позиции, включать транзитивный поиск и видеть причины блокировки               |
| Конфигурации                 | Сохранять, просматривать, полностью изменять, копировать, выгружать в JSON и безвозвратно удалять сборки                              |
| Интерфейс                    | Работать на компьютере и телефоне, выбирать светлую, тёмную или системную тему, русский или английский язык                           |

В одной сборке может находиться не более одного компонента каждого типа. Для сохранения выбранные компоненты должны
образовывать связный граф подтверждённых отношений, а применимые автоматические правила не должны запрещать ни одну
пару. Наличие прямой связи между каждой парой не требуется.

Системное имя атрибута уникально внутри предметной области с учётом регистра. Если одна характеристика нужна нескольким
типам, следует подключить к ним существующее определение из общего каталога, а не создавать дубликаты.

## Установка готового пакета

Поддерживаются Windows 10/11 x86-64 и macOS на процессорах Intel и Apple Silicon. Требуется установленный и запущенный
Docker Desktop. JDK, Gradle, Node.js, npm и Git пользователю не нужны.

1. Откройте [выпуски проекта](https://github.com/eltgm/configurator-root/releases) и скачайте архив `v1.2.0` для своей
   операционной системы.
2. Полностью распакуйте каталог `Configurator` в место с правом записи.
3. В Windows запустите `Start.cmd`, в macOS — `Start.command`.
4. Дождитесь сообщения о готовности. Браузер откроет <http://127.0.0.1:8080>.

На macOS при первом предупреждении Gatekeeper используйте правый щелчок по файлу и команду «Открыть». Не отключайте
системную защиту.

В пакет также входят команды:

| Команда   | Назначение                                                                            |
| --------- | ------------------------------------------------------------------------------------- |
| `Stop`    | Остановить приложение без удаления данных                                             |
| `Update`  | Создать обязательную резервную копию и обновить контейнеры стабильного канала         |
| `Backup`  | Создать резервную копию PostgreSQL и MinIO с контрольными суммами                     |
| `Restore` | Проверить копию, создать страховочную копию текущих данных и выполнить восстановление |

Резервные копии не зашифрованы. Подробные правила установки, обновления, восстановления и удаления приведены в
[руководстве по локальной поставке](docs/release/LOCAL_DELIVERY.md).

## Быстрый запуск из исходного кода

Для запуска понадобятся JDK 21 и Docker Desktop с подключаемым модулем Compose. Серверная часть собирается через
Gradle Wrapper, а пользовательский интерфейс — внутри образа шлюза.

```bash
./gradlew :configurator:bootJar
docker compose up -d --build
```

После запуска доступны:

- приложение — <http://127.0.0.1:8080>;
- описание OpenAPI через шлюз — <http://127.0.0.1:8080/api/v3/api-docs>.

Основная конфигурация Compose публикует только локальный порт шлюза. Серверная часть, PostgreSQL и MinIO остаются во
внутренней сети Docker.

### Среда разработки

Чтобы открыть прямой доступ к контейнерам только через локальные адреса, добавьте конфигурацию разработки:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

Будут доступны:

- серверная часть и Swagger UI — <http://127.0.0.1:8081/swagger-ui/index.html>;
- PostgreSQL — `127.0.0.1:5432/configurator`;
- API MinIO — <http://127.0.0.1:9000>;
- панель MinIO — <http://127.0.0.1:9001>.

Значения `configurator/configurator` и `minioadmin/minioadmin` предназначены только для локальной разработки.

### Пользовательский интерфейс в режиме разработки

После запуска серверной части откройте второй терминал. Требуются Node.js 24 LTS и npm 11.

```bash
cd configurator-web
npm ci
npm run dev
```

Интерфейс откроется на <http://127.0.0.1:5173>. Сервер Vite передаёт запросы `/api/*` серверной части на
`http://127.0.0.1:8080` с удалением префикса `/api`.

### Запуск серверной части из IntelliJ IDEA

Поднимите только PostgreSQL и MinIO, затем запустите главный класс Spring Boot из среды разработки:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d postgres minio
```

Шлюз в этом случае запускать не следует: приложение из IntelliJ IDEA занимает `127.0.0.1:8080`. При необходимости
задайте переменные среды в конфигурации запуска.

## Настройка

| Переменная                 | Значение по умолчанию                           | Назначение                |
| -------------------------- | ----------------------------------------------- | ------------------------- |
| `DB_URL`                   | `jdbc:postgresql://localhost:5432/configurator` | адрес JDBC                |
| `DB_USER`                  | `configurator`                                  | пользователь БД           |
| `DB_PASSWORD`              | `configurator`                                  | пароль БД                 |
| `IMAGE_STORAGE_ENDPOINT`   | `http://localhost:9000`                         | внутренний адрес MinIO/S3 |
| `IMAGE_STORAGE_ACCESS_KEY` | `minioadmin`                                    | ключ доступа              |
| `IMAGE_STORAGE_SECRET_KEY` | `minioadmin`                                    | секретный ключ            |
| `IMAGE_STORAGE_BUCKET`     | `configurator-components`                       | контейнер изображений     |

Максимальный размер одного изображения — 10 МБ. Первое изображение галереи считается заглавным. В каталоге и
конфигураторе используются PNG-превью размером до 512 × 512 пикселей, а при увеличении открывается оригинал.
[Подробнее об изображениях](docs/requirements/component-primary-images.md).

## Архитектура и состав репозитория

Серверная часть следует слоистой архитектуре с гексагональными границами:

```text
controller -> facade -> service -> outbound port -> infrastructure
```

- `api.inbounds.rest` — граница HTTP, созданные из OpenAPI интерфейсы и транспортные DTO;
- `application.facade` — преобразование транспортных и доменных моделей;
- `application.service` — прикладные сценарии и деловые правила;
- `application.port.out` — интерфейсы хранилищ и внешних зависимостей;
- `domain` — доменные модели и ошибки;
- `infrastructure` — работа с jOOQ/PostgreSQL, MinIO и текущим пользователем.

Границы проверяются тестами ArchUnit. Файлы в `build/generated/**` создаются автоматически и вручную не изменяются.

```text
.
├── configurator/                   # приложение Spring Boot
├── configurator-integration-tests/ # общие локальные и внешние контрактные проверки
├── configurator-web/               # интерфейс React/Vite
├── delivery/                       # шаблоны пользовательских пакетов Windows и macOS
├── specs/configurator-api.yaml     # источник истины REST API
├── docs/                           # руководства, требования и материалы выпусков
├── .github/                        # непрерывная интеграция и подготовка выпусков
├── docker-compose.yml
└── Dockerfile
```

Основные источники истины:

- REST API — [`specs/configurator-api.yaml`](specs/configurator-api.yaml);
- схема БД — [`configurator/src/main/resources/db/migration`](configurator/src/main/resources/db/migration);
- обязательные правила для AI-агентов — [`AGENTS.md`](AGENTS.md).

## Проверка проекта

Полная локальная проверка серверной части и общих контрактов:

```bash
./gradlew build
```

Для неё должен быть доступен Docker, поскольку интеграционные проверки используют Testcontainers.

Внешние контрактные проверки через рабочий шлюз:

```bash
./gradlew :configurator:bootJar
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
./gradlew :configurator-integration-tests:externalIntegrationTest
```

Проверка пользовательского интерфейса:

```bash
cd configurator-web
npm ci
npm run check
npm run test:coverage
```

Проверки в браузере и собранной поставке описаны в
[руководстве по проверке интерфейса](docs/testing/FRONTEND_TESTING.md).

## Разработка и выпуски

Изменения выполняются в ветках `feature/CON<версия>-<номер>` или `bugfix/CON<версия>-<номер>` от `develop` и
передаются запросом на слияние в `develop`. Изменение REST API начинается со спецификации OpenAPI, изменение БД — с
новой миграции Flyway. Подробные правила приведены в [руководстве участника разработки](CONTRIBUTING.md).

Проект следует Semantic Versioning. Стабильные версии собираются только из `master` по аннотированному тегу
`vX.Y.Z`. История изменений находится в [CHANGELOG.md](CHANGELOG.md), материалы текущего выпуска — в
[`docs/release`](docs/release).
