**План исправления UI/UX Configurator**

Статус: подтверждён пользователем и реализован в feature/CON1-147. Результаты и ограничения — в [отчёте реализации](UI_UX_IMPLEMENTATION_2026-09-09.md). Выбраны смешанная аудитория, предупреждение о потере изменений, мобильная панель, быстрый просмотр и расширение API/backend.

Основание: [аудит от 9 сентября 2026](UI_UX_AUDIT_2026-09-09.md), UX-01–UX-17. Цель — закрыть все замечания с проверяемым результатом, сохранив правила совместимости, учёта количества и локальной поставки.

**Согласованные решения и рассмотренные альтернативы**

| Вопрос | Предлагаемый вариант | Влияние альтернативы |
| --- | --- | --- |
| Аудитория | Смешанная: простой основной сценарий, дополнительные настройки для специалистов | Приоритет новичков увеличивает объём onboarding; приоритет специалистов — плотность списков |
| Несохранённые формы | Подтверждение только при наличии изменений: остаться / отбросить | Черновики на сессию или между запусками потребуют отдельной политики хранения, версий и очистки |
| Мобильная настройка | Панель со всеми разделами из общей модели навигации | Обзорная страница меняет маршрутизацию и переходы, но тоже решает проблему |
| Выбор компонентов | Три ключевых атрибута в карточке и быстрый просмотр | Сравнение до трёх моделей — дополнительный сценарий; администрирование состава ключевых атрибутов может потребовать миграции |
| API/backend | Совместимое расширение поиска/сортировки конфигураций и данных кандидатов | Frontend-only оставляет серверный поиск UX-10 незавершённым; не подменять его поиском по текущей странице |

Пользователь подтвердил все пять решений и реализацию. Следующий свободный номер проверен по локальным и удалённым веткам: создана feature/CON1-147.

**Границы изменений до реализации**

- Рабочая ветка при составлении плана — develop. Имеющиеся незакоммиченные файлы аудита в docs/reviews сохранить. Для реализации выбрана feature/CON1-147; прямого push в develop/master не выполнять.
- OpenAPI потребуется для полноценного серверного поиска/сортировки, а также предпочтительного получения характеристик кандидатов без отдельных запросов на каждую карточку.
- В основном предложенном варианте изменение схемы БД не требуется: поиск и атрибуты используют существующие данные. Индексы добавлять новой Flyway-миграцией только при обоснованной необходимости; старые миграции не менять.
- Если пользователь выбирает администрируемые ключевые характеристики, конкретную модель хранения и миграцию включить в итоговый план до его подтверждения.
- После изменения OpenAPI backend и frontend генерируются штатными командами. Build/generated не редактировать; generated SDK не менять вручную.
- Сохранить controller → facade → service → outbound port → infrastructure. REST DTO не переносить в сервисы/домен, jOOQ не выводить за persistence boundary.
- Параметры списков можно хранить в URL; domainId остаётся вне URL. Query keys, клиентское состояние фильтров и черновики изолировать по области.
- Сохранить light/dark/auto, RU/EN, единые providers и Mantine tokens. Все новые пользовательские строки — в translations.
- Правила прямой/транзитивной совместимости, остатков, резервирования, JSON-экспорта, безопасности и release policy остаются действующими. Их изменение не входит в исправления интерфейса.

**Этап 1. Контекст области и защита введённых данных**

Закрывает UX-01, UX-02, UX-06. Сначала защитить данные, затем менять представление.

1. Ограничить keepPreviousData переходами внутри одной области. На смене domainId показывать загрузку новой области, убирать прежние результаты и связанные действия/подтверждения. Проверить другие списки с placeholderData и изменения области на карточках/формах.
2. Подключить регистрацию несохранённых изменений к форме автоматического правила. Проверить создание, редактирование, Back, переход через меню, смену области, перезагрузку и закрытие вкладки.
3. Ввести согласованное поведение закрытия изменённых модальных форм: атрибуты, типы, области, ручные связи, создание/копирование конфигурации. Пустая форма закрывается сразу; изменённая следует выбранной политике.
4. Для рекомендованного варианта использовать общий механизм подтверждения, без конкурирующих route blockers. Сохранять значения при отмене отказа, корректно восстанавливать фокус. При активном запросе сохранять существующую защиту повторного submit/закрытия.

Приёмка: при медленной загрузке/ошибке B невозможно архивировать объект A из интерфейса B; отменённый уход сохраняет каждое поле; подтверждённый уход не переносит ID между областями. Существующий черновик сборки остаётся доступным после обновления приложения.

Проверки: отдельные mocks для разных domainId; задержка и ошибка ответа; изменение области с открытым диалогом; dirty/pristine формы; Escape, фон, крестик, Cancel, Back и beforeunload. В native beforeunload использовать возможности браузера, не обещать одинаковый текст системного диалога во всех браузерах.

**Этап 2. Навигация, возврат и клавиатурное взаимодействие**

Закрывает UX-03, UX-04, UX-05, UX-07, UX-13, UX-16.

1. Мобильный пункт «Настройка» открывает выбранный пользователем вариант полного меню; источником остаётся settingsNavigation. Скрытая desktop-панель не участвует в Tab и дереве доступности. Предусмотреть закрытие меню, выбор маршрута и изменение breakpoint.
2. Вычислять активный раздел для вложенных маршрутов с границами сегментов. Раздел и текущую страницу не смешивать в aria-current. Добавить понятный возврат в списки; breadcrumbs использовать там, где они помогают иерархии.
3. Убрать размонтирование браузера кандидатов на каждое изменение состава. Сохранять поиск и фильтр типа; если страница стала недоступной, переводить на допустимую. При смене области сбрасывать контекст либо восстанавливать только её собственное состояние.
4. После добавления/удаления/замены сохранять фокус на существующем действии либо переводить его на следующий осмысленный элемент/заголовок. Не позволять фоновому refetch перехватывать фокус. Announcements отражают результат и изменение количества кандидатов.
5. Состояние каталога — поиск, тип, архив, страница — хранить в нормализованных query parameters с областью как внешним контекстом. Back/Forward и «К списку» восстанавливают список и прокрутку. Debounce поиска не создаёт запись истории на каждый символ; отдельно проверить восстановление после reload и смены области.
6. Передать refs контролируемым Select/NumberInput, связать поля с ошибками; after-submit переводить фокус к первой ошибке или к сводке. Не менять фокус при обычной фоновой проверке ввода.
7. Для повторяющихся действий добавить доступные имена с названием объекта, сохранив видимый текст в accessible name. Проверить добавление, удаление из сборки, архивирование, восстановление и меню карточек.

Приёмка: полный сценарий поиска → детали → возврат → подбор → замена → сохранение выполним клавиатурой; нет фокуса вне viewport и ухода на BODY после мутаций; пользователь видит текущий раздел на вложенной странице.

Проверки: последовательный Tab/Shift+Tab и Enter/Escape, а не только программный focus; переходы в Chromium/Firefox/WebKit; узкий viewport; смена ориентации; сокращение выдачи после фильтра/добавления; оба режима совместимости.

**Этап 3. Мобильный конфигуратор и помощь**

Закрывает UX-08, UX-14; использует исправленную навигацию этапа 2.

1. Для пустой сборки поставить поиск/выбор компонентов впереди крупного empty state. Для заполненной — компактный итог с числом моделей, статусом, входом в состав и сохранением.
2. На телефоне предусмотреть быстрое переключение «Подбор / Сборка» или раскрытие состава без длинной прокрутки. Предлагаемый вариант — подбор как основной блок и раскрываемая сборка; уточнить после ответа об аудитории.
3. Дополнительную настройку транзитивности поместить в раскрываемые параметры. Режим учёта количества и его последствия оставить понятными до сохранения; не скрывать предупреждения о дефиците или несовместимости.
4. Упростить тексты до описания результата. Сохранить точность: разрешённые через цепочку кандидаты не должны обещать возможность сохранения несвязной сборки.
5. Добавить доступный вход в помощь в общем интерфейсе, короткие примеры, а для новой области — маршрут настройки «типы/атрибуты → компоненты → совместимость → сборка» с переходами. Help доступна в локальной поставке и не зависит от внешнего сайта.
6. Крупные notices сделать компактными, но не прятать сообщения о потере возможности хранить черновик и ошибки загрузки.

Приёмка: на 390 × 844 первый выбор достижим на первом экране или одним очевидным действием; при 20–50 моделях следующий компонент можно добавить без пролистывания всего состава. Фиксированные элементы учитывают safe area и не перекрывают focus, ошибки и экранную клавиатуру.

Проверки: пустая/заполненная/конфликтная сборка, учёт количества включён/выключен, 320/390/768/1440 px, RU/EN, light/dark, reduced motion, landscape. Короткий walkthrough по новой области и demo без внешней документации.

**Этап 4. Информативный выбор компонентов и плотность карточек**

Закрывает UX-09, UX-17. Зависит от выбранного объёма сравнения и разрешённых изменений API.

1. В основном варианте показывать до трёх характеристик в порядке, уже заданном атрибутам типа; детерминированно обрабатывать отсутствующий порядок/значение. Не придумывать универсальные характеристики, специфичные только для ПК. Это начальная политика выбора, а не новая настройка БД.
2. Добавить быстрый просмотр модели в доступной панели с полным названием, характеристиками, изображением и остатком. Его закрытие возвращает в тот же список, к тому же элементу. Сохранить обычную ссылку на полную карточку.
3. Данные для характеристик предоставлять согласованно в начальном каталоге, прямом, транзитивном и множественном подборе. Предпочтение — совместимо расширить соответствующие ответы API и получать атрибуты пакетно. Не запускать запрос деталей на каждую модель всего каталога.
4. Если выбран отдельный экран сравнения: ограничить сравнение тремя моделями, держать выбор в контексте области, объяснять сравнение разных типов, показывать общие характеристики и различия. Добавить удаление/замену участника и доступное мобильное представление.
5. Если выбрана настройка характеристик администратором: перед реализацией зафиксировать хранение, API, миграцию, порядок и поведение при удалении/отвязке атрибута. Существующие значения характеристик не изменять.
6. Для отсутствующего изображения использовать компактный placeholder. Полное название должно быть доступно на touch и с клавиатуры без hover-only tooltip. Сохранить пользовательское предпочтение карточки/таблица.

Приёмка: похожие модели различимы по ключевым данным без посещения каждой карточки; быстрый просмотр не теряет сборку и фильтры. Ошибка загрузки подробностей не блокирует остальной список. Представление остаётся стабильным до и после загрузки изображения.

**Этап 5. Поиск конфигураций и полные списки кандидатов**

Закрывает UX-10, UX-11. Нужен согласованный API для полного закрытия UX-10.

1. Расширить GET /domains/{id}/configurations необязательными параметрами name, sortBy и sortDirection. Предлагаемая семантика: поиск подстроки без учёта регистра в названии; сортировка по createdAt/name, asc/desc. Без параметров сохранить нынешний createdAt desc, id desc.
2. Валидировать параметры, использовать whitelist сортировки и безопасные SQL expressions. Поиск и totalItems считают один и тот же набор с текущими domainId/userId/trackInventory. Literal % и _ обрабатывать как пользовательский текст; порядок при равных значениях стабилизировать ID.
3. Провести изменение через controller/facade/service/port/jOOQ, обновить общий local/external integration contract. Проверить существующие вызовы без новых параметров.
4. Во frontend добавить поиск, сортировку, сброс фильтров и различимые состояния «ещё нет конфигураций»/«ничего не найдено». Query keys включают все параметры и domainId. Смена фильтра возвращает на первую страницу.
5. В карточке конфигурации показывать краткий состав, например первые три позиции и «Ещё N», с доступным раскрытием; не выводить десятки компонентов в каждой карточке по умолчанию.
6. Для заблокированных кандидатов добавить отдельное «Показать ещё» порциями по 12, отображать «Показано N из M» и сохранять доступность всех причин. При смене фильтра/сборки пересчитывать этот счётчик независимо от пагинации доступных моделей.

Приёмка: конфигурация находится среди 1000 записей, в том числе за пределами первой страницы; поиск/сортировка сочетаются с inventory-фильтром и не смешивают области. Для 13/25/100 заблокированных кандидатов достижимы все элементы, без изменения правил совместимости.

Если выбран frontend-only, выполнить компактное представление и полный список блокировок, но явно оставить серверную часть UX-10 незакрытой. Такой вариант не считать полным выполнением всех 17 пунктов.

**Этап 6. Контекстные ошибки и touch-управление**

Закрывает UX-12, UX-15; применить общий подход к изменённым формам и диалогам.

1. Выводить ошибку мутации внутри диалога/формы до повторной попытки или изменения контекста. Для 409 объяснять препятствие и дальнейший шаг; Retry предлагать только при осмысленном повторе.
2. Согласовать локальные ошибки с глобальным MutationCache: предотвращать повторяющиеся уведомления об одной ошибке, сохраняя общий fallback для сценариев без локального отображения. Не удалять глобальную обработку ошибок целиком.
3. Увеличить области touch-нажатия небольших иконок примерно до 44 × 44 CSS px, сохранив сами иконки компактными и отделив разрушительные действия.
4. Проверить повторный submit, loading/disabled состояния, длинные русские сообщения, исчезновение toast, возврат фокуса и сочетание панели/диалога.

Приёмка: пользователь понимает отказ операции после исчезновения уведомления; ошибку слышит экранный диктор без дублирования; соседние редактирование/удаление легко нажимаются на 320 px.

**Этап 7. Регрессия и сдача результата**

Каждый исправленный дефект получает проверку своего пользовательского сценария. Для чисто визуальных низкорисковых изменений отдельные unit-тесты, повторяющие CSS, не нужны: использовать браузерные измерения и визуальную проверку.

| Контур | Обязательная проверка/результат |
| --- | --- |
| Frontend toolchain | npm ci, npm run check; check включает api:check, формат, ESLint, Stylelint, unit и build |
| Coverage | npm run test:coverage; новые ветви guards, filters и API normalization покрыты осмысленными случаями |
| E2E | npm run test:e2e; Chromium, Firefox, WebKit, ключевые переходы по UI |
| Accessibility | npm run test:accessibility, ручная клавиатура, focus visibility, zoom/reflow, language/theme, доступные имена |
| Visual | npm run test:visual только в pinned Docker; ожидаемые изменения baseline через test:visual:update с просмотром diff, без слепого принятия снимков |
| Backend/API | При выбранном расширении: ./gradlew build и ./gradlew :configurator-integration-tests:externalIntegrationTest; единые local/external scenarios и ArchitectureTest |
| Реальная поставка | npm run test:delivery на полном Compose; проверить реальные API, deep links и ключевой путь сохранения |
| Delivery scripts | Шесть contract scripts из AGENTS.md, если потребуется менять delivery/Compose/gateway/package builder; в основном плане такие изменения не предусмотрены |
| Большие данные | Проверить 50 моделей сборки, 1000 конфигураций, длинные имена, 13+ блокировок; измерить интерактивность без заявления полевых Core Web Vitals |

Нужные fixtures создаются в тестовом контуре, не в пользовательских данных. Недоступный внешний контур или физическое устройство отметить как непроверенное, а не как успешный тест. VoiceOver/NVDA и реальные телефоны включить в ручную приёмку по доступности окружения.

**Критерий завершения**

- Каждый UX-01–UX-17 имеет статус «исправлено», ссылку на изменение и фактически выполненную проверку; при осознанном переносе пункта статус остаётся открытым.
- Нет регрессий области/совместимости/остатков/сохранения; UI работает в двух языках и темах.
- OpenAPI/client синхронизированы; миграции, если потребуются по согласованному варианту, новые и воспроизводимые.
- Обновлены затронутые пользовательское руководство и документ accessibility; показатели и ограничения описаны по фактической проверке.
- Итог содержит изменения, влияние на OpenAPI/БД, результаты проверок, непроверенные контуры и оставшиеся блокеры. Публикация релиза и push в защищённые ветки не являются частью этой задачи.

При выполнении основного варианта сохраняются trusted-local scope и существующее ограничение runtime-аутентификации. Исправления UI/UX не расширяют продуктовый контракт на LAN/public/server deployment.
