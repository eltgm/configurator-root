# Epic 9 — Пользовательский интерфейс и локальная поставка

## Цель

Предоставить актуальный и функциональный UI для локального однопользовательского использования Configurator на
Windows x86-64 и macOS Intel/Apple Silicon. Конечному пользователю требуются только Docker Desktop, доступ в интернет и
скачанный архив GitHub Release; Java, Gradle и Node.js устанавливать не нужно.

## Принятые продуктовые решения

- пользовательское название `Domain` — «Предметная область»;
- один пользователь одновременно управляет каталогом и собирает конфигурации;
- конфигуратор работает свободно, без обязательной последовательности типов;
- для нескольких выбранных компонентов используется пересечение наборов совместимости;
- транзитивная совместимость включается отдельно и не считается достаточной для сохранения конфигурации;
- граф и автоматические правила находятся в разделе «Настройка»;
- сохранённую конфигурацию можно полностью редактировать, копировать, экспортировать и безвозвратно удалять;
- компоненты можно архивировать, просматривать в архиве и восстанавливать;
- изображения можно загружать, удалять и переставлять;
- каталог поддерживает режимы «Карточки» и «Таблица»;
- последняя предметная область открывается автоматически и остаётся доступен переключатель области;
- интерфейс поддерживает светлую, тёмную и системную темы;
- минимальная поддерживаемая ширина — 360 px;
- основной язык первого релиза — русский, структура должна быть готова к локализации;
- runtime-аутентификация в первый frontend-релиз не входит.

## Технологический стек frontend

- React 19.2;
- TypeScript 6.0 (последняя версия, поддерживаемая актуальным typescript-eslint);
- Vite 8.2;
- React Router 7.18 (актуальная стабильная линия; версия 8 ещё не опубликована);
- Mantine 9;
- TanStack Query;
- React Hook Form и Zod 4;
- React Flow 12 (`@xyflow/react`);
- OpenAPI-generated types и typed client;
- Zustand только при необходимости общего состояния конфигуратора;
- Vitest, Testing Library и MSW;
- Playwright для E2E;
- Node.js 24 LTS и npm с `package-lock.json`;
- ESLint flat config, Prettier и Stylelint.

## Архитектура поставки

- frontend размещается в монорепозитории в отдельном каталоге `configurator-web` и не становится Gradle-модулем;
- production frontend собирается в статические файлы;
- отдельный web gateway раздаёт SPA и проксирует `/api/*` во внутренний backend;
- единственная внешняя точка входа — `http://127.0.0.1:8080`;
- PostgreSQL, MinIO и backend не публикуются наружу;
- браузер не обращается к MinIO напрямую;
- release images собираются для `linux/amd64` и `linux/arm64`;
- пользователь получает отдельные архивы Windows и macOS со сценариями Start, Stop, Update, Backup и Restore;
- данные сохраняются в именованных Docker volumes.

## Информационная архитектура

Основное меню выбранной предметной области:

1. Конфигуратор.
2. Компоненты.
3. Конфигурации.
4. Настройка:
   - типы и атрибуты;
   - ручная совместимость;
   - автоматические правила;
   - граф совместимости;
   - параметры предметной области.

На телефоне используется нижняя навигация. Табличный каталог преобразуется в компактный список без горизонтальной
прокрутки.

#### 9.2 — Удаление и атомарная перестановка изображений

- `DELETE /component-images/{id}` безвозвратно удаляет объект из MinIO и metadata из PostgreSQL;
- объект удаляется до metadata; ошибка хранилища возвращает `503` и сохраняет metadata для повторной попытки;
- `PUT /components/{id}/images/order` принимает полный итоговый массив `imageIds`;
- идентификаторы должны быть положительными, уникальными и точно совпадать с текущим набором изображений компонента;
- сервер атомарно назначает непрерывные `orderIndex` от `0` до `n-1` и возвращает итоговый массив изображений;
- пустой массив допустим только для пустой галереи;
- удаление и перестановка изображений архивного компонента возвращают `409`;
- неизвестное изображение при удалении или неизвестный компонент при перестановке возвращают `404`.

#### 9.3 — Просмотр архива и восстановление компонентов

- `GET /domains/{domainId}/components` принимает необязательный query-параметр `archived`;
- `archived=true` возвращает только архив, `false` — только активные компоненты;
- отсутствие `archived` сохраняет обратную совместимость и возвращает обе группы;
- фильтр архива совместим с фильтрами типа, имени и пагинацией;
- `POST /components/{id}/restore` идемпотентно снимает архивный флаг и возвращает полный `Component`;
- восстановление сохраняет атрибуты, изображения, совместимость и ссылки сохранённых конфигураций;
- повторное восстановление активного компонента возвращает его без дополнительной записи в БД;
- неизвестный компонент возвращает `404`, некорректный идентификатор — `400`.

#### 9.4 — Полное редактирование сохранённой конфигурации

- `PUT /configurations/{id}` полностью заменяет название, описание и состав сохранённой конфигурации;
- запрос принимает обязательные `name`, `componentIds` и необязательное nullable `description`;
- `domainId`, владелец и `createdAt` не изменяются и не принимаются от клиента;
- весь итоговый состав строго повторно проверяется по правилам создания конфигурации;
- архивный компонент возвращает `409`, даже если он уже входил в сохранённую конфигурацию;
- идентификаторы компонентов должны быть положительными и уникальными; компоненты должны принадлежать предметной
  области, быть активными, иметь разные типы и быть попарно напрямую совместимыми; транзитивной совместимости
  недостаточно;
- обновление metadata и полная замена связей компонентов выполняются атомарно;
- чужая или неизвестная конфигурация возвращается как `404`; неуспешная проверка не изменяет исходные данные;
- успешный ответ `200` возвращает полную актуальную конфигурацию.

#### 9.5 — Безвозвратное удаление сохранённой конфигурации

- `DELETE /configurations/{id}` безвозвратно удаляет конфигурацию текущего пользователя;
- успешное удаление возвращает `204 No Content` с пустым телом;
- связи конфигурации с компонентами удаляются каскадно, сами компоненты каталога не изменяются;
- другие конфигурации и предметная область не затрагиваются;
- неизвестная, чужая или уже удалённая конфигурация возвращает `404`;
- неположительный идентификатор возвращает `400`.

#### 9.6 — Структурированные коды и детали API-ошибок

- все JSON-ошибки сохраняют поля `timestamp`, `status`, `error`, `message`, `path` и дополнительно возвращают обязательные
  `code` и `details`;
- `code` — стабильный машинно-читаемый код причины, не зависящий от HTTP reason phrase и текста сообщения;
- верхнеуровневые коды различают неизвестную бизнес-ошибку, внутреннюю ошибку, отсутствие сущности, каждый поддержанный
  вид конфликта, ошибку валидации, размер/формат изображения и недоступность внешнего хранилища;
- `details` всегда является массивом; для ошибок без дополнительных деталей возвращается пустой массив;
- элемент `details` содержит обязательные `code`, `message` и необязательный `field` для привязки ошибки к полю формы;
- ошибки Bean Validation возвращаются отдельными деталями, дедуплицируются и сортируются детерминированно; constraint code
  нормализуется в `UPPER_SNAKE_CASE`;
- отсутствующий параметр/part, несовпадение типа и нечитаемое JSON-тело получают отдельные detail codes;
- существующие HTTP statuses и безопасные человекочитаемые сообщения сохраняются для обратной совместимости;
- ответы не содержат rejected values, stack trace, внутренние причины и сообщения внешнего хранилища;
- формат фиксируется в OpenAPI и проверяется единым local/external integration contract.

#### 9.7 — Создание демонстрационной предметной области

- `POST /domains/demo` без тела создаёт демонстрационную предметную область «Сборка ПК» и возвращает её с
  `201 Created`;
- повторный запрос не создаёт копию и возвращает `409 ENTITY_ALREADY_EXISTS`;
- вся операция с данными PostgreSQL атомарна: ошибка любого шага откатывает домен и все зависимые записи;
- владельцем создаваемого домена и сохранённой конфигурации становится текущий пользователь из `CurrentUserProvider`;
- набор содержит шесть типов: процессор, материнская плата, оперативная память, видеокарта, блок питания и корпус;
- для каждого типа создаются определения атрибутов и два компонента, всего двенадцать компонентов;
- среди компонентов присутствуют намеренно несовместимые варианты по сокету, DDR4/DDR5, мощности БП и размеру корпуса;
- создаются автоматические правила для сокета, стандарта памяти, форм-фактора, мощности БП и длины видеокарты;
- ручные связи дополняют прямую попарную совместимость готовой конфигурации там, где автоматическое правило не
  применяется;
- создаётся сохранённая конфигурация «Игровой ПК 1440p» из шести совместимых компонентов разных типов;
- граф, поиск, пересечение и экспорт используют созданные данные через существующие read API;
- изображения не входят в набор: внешнее хранилище не может быть атомарно откатано общей DB-транзакцией;
- endpoint проверяется единым local/external integration contract, включая состав набора и повторный конфликт.

#### 9.8 — Создание `configurator-web` и настройка toolchain

- frontend создаётся в отдельном каталоге `configurator-web` и не включается в Gradle multi-project;
- используется Node.js 24 LTS, npm и committed `package-lock.json`; `package.json` ограничивает поддерживаемые версии
  Node/npm через `engines`;
- React 19.2 собирается Vite 8.2, TypeScript работает в strict mode и не генерирует JavaScript через `tsc`;
- TypeScript 6.0 используется до появления официальной поддержки TypeScript 7 в актуальном typescript-eslint;
- настроены алиас `@/`, dev server на `127.0.0.1:5173` и proxy `/api/*` на локальный backend с удалением префикса
  `/api`;
- ESLint flat config, Prettier и Stylelint запускаются отдельными командами и входят в единый `npm run check`;
- Vitest работает в jsdom, Testing Library и MSW подключены через общий test setup;
- Playwright получает smoke-конфигурацию для Chromium, Firefox и WebKit, но установка browser binaries остаётся явной
  командой разработчика;
- production build создаётся в `configurator-web/dist`, а generated reports и зависимости игнорируются Git;
- минимальный экран и тест подтверждают работоспособность React entrypoint; AppShell, темы, локализация и маршрутизация
  относятся к 9.10;
- OpenAPI client и связанные dependencies не входят в 9.8 и добавляются в 9.9;
- полный frontend quality gate: `npm ci && npm run check`; E2E запускаются отдельно после `npx playwright install`.

#### 9.9 — Генерация типизированного клиента из OpenAPI

- единственным источником REST-контракта остаётся `specs/configurator-api.yaml`; ручные frontend DTO и ручное описание
  endpoint-функций запрещены;
- `@hey-api/openapi-ts` генерирует TypeScript-модели, типизированные SDK-функции и Fetch-клиент в
  `src/shared/api/generated`;
- generated-каталог коммитится для воспроизводимой сборки, полностью очищается при повторной генерации и не
  редактируется вручную;
- сгенерированный клиент использует относительный `baseUrl=/api`, чтобы dev-запросы проходили через Vite proxy, а
  production deployment мог обслуживать UI и API на одном origin;
- handwritten boundary `src/shared/api/index.ts` является единственной точкой импорта generated API для прикладного
  frontend-кода и экспортирует SDK, типы и singleton клиента;
- команда `npm run api:generate` пересоздаёт клиент, `npm run api:check` выполняет генерацию во временный каталог и
  завершается ошибкой при расхождении со committed output;
- drift-check входит в `npm run check`; изменение OpenAPI требует локально выполнить `npm run api:generate` и
  закоммитить результат вместе с изменением спецификации;
- generated-код исключается из ESLint и получает воспроизводимый `@ts-nocheck` как внешний артефакт, чтобы внутренние
  шаблоны клиента не ослабляли `exactOptionalPropertyTypes` для handwritten-кода; output форматируется Prettier, а
  API boundary и потребители проходят общий TypeScript build; generated runtime также исключается из метрики unit
  test coverage;
- runtime-тест через MSW подтверждает относительный base URL, сериализацию query-параметров и типизированный ответ;
- генератор и его транзитивные зависимости не должны добавлять известные high/critical уязвимости; security override
  допускается только узко для конкретной исправленной транзитивной версии и документируется в `package.json`;
- TanStack Query hooks, единая модель ошибок и auth interceptor не входят в 9.9 и добавляются в 9.11 и задаче
  авторизации соответственно.

#### 9.10 — Маршрутизация, AppShell, темы и локализация

- React Router использует стабильные человекочитаемые маршруты `/configurator`, `/components`, `/configurations` и
  `/settings/*`; выбранная предметная область остаётся глобальным контекстом и не кодируется в URL;
- `/` перенаправляет на `/configurator`, неизвестный адрес показывает локализованную страницу 404 с возвратом в
  конфигуратор;
- настройки разделены на `/settings/types`, `/settings/compatibility/manual`,
  `/settings/compatibility/rules`, `/settings/compatibility/graph` и `/settings/domain`;
- в 9.10 маршруты отображают информативные placeholder-экраны; загрузка предметных данных начинается с 9.12;
- Mantine AppShell содержит header, desktop sidebar, main content и mobile bottom navigation; layout поддерживает
  ширину от 360 px без горизонтальной прокрутки;
- desktop navigation показывает все разделы и вложенные настройки, mobile navigation — четыре верхнеуровневых пункта:
  конфигуратор, компоненты, конфигурации и настройки;
- текущий маршрут визуально выделен и обозначен `aria-current`; навигация и controls доступны с клавиатуры и имеют
  доступные имена;
- header показывает название приложения, текущий placeholder предметной области и меню пользовательских настроек;
  реальный выбор и сохранение последней предметной области реализуются в 9.12;
- тема поддерживает режимы `system`, `light` и `dark`, по умолчанию следует системной настройке и сохраняется в
  `localStorage` через Mantine color scheme manager;
- локализация реализована на i18next/react-i18next; русский является языком по умолчанию, английский подтверждает
  расширяемость структуры, выбранный язык сохраняется локально;
- все пользовательские строки AppShell, навигации, placeholder-экранов, document title и 404 берутся из translation
  resources;
- route tree, desktop/mobile navigation, 404, тема и переключение языка покрываются component tests;
- API, TanStack Query, server state, notifications и общая обработка ошибок не входят в 9.10.

#### 9.11 — Серверное состояние, обработка ошибок и базовые UI-компоненты

- TanStack Query является единственным общим механизмом хранения server state; предметные данные не дублируются в
  глобальных React context или локальных store;
- `QueryClient` создаётся через тестируемую factory и подключается на уровне application providers; запросы имеют
  ограниченный retry только для сетевых и серверных ошибок, мутации автоматически не повторяются;
- первоначальная ошибка query отображается в контексте экрана, а ошибка фонового обновления при уже имеющихся данных
  показывается уведомлением и не скрывает сохранённые в кэше данные;
- все ошибки generated Fetch-клиента преобразуются в единую handwritten-модель: структурированный `ErrorResponse`,
  сетевая ошибка и неизвестная ошибка различаются без разбора человекочитаемого текста;
- модель сохраняет HTTP status, `ApiErrorCode` и `details`, определяет возможность retry и позволяет получить field
  errors для форм; неизвестные технические сообщения и stack trace пользователю не показываются;
- машинные коды API отображаются в локализованные пользовательские заголовки, а безопасное сообщение backend может
  использоваться как дополнительное описание;
- ошибки мутаций централизованно показываются через Mantine Notifications; success-уведомления вызываются предметным
  сценарием явно, чтобы текст описывал реально выполненное действие;
- предоставляются повторно используемые доступные компоненты `PageHeader`, `LoadingState`, `EmptyState`, `ErrorState`
  и `ServerDataState`; состояния имеют корректные live-region/role, действие retry и поддерживают mobile layout;
- необработанная ошибка рендера/маршрута показывает локализованный безопасный fallback с возможностью вернуться в
  конфигуратор;
- Query policy, нормализация API/сетевых/неизвестных ошибок, field details, notifications и все базовые UI-состояния
  покрываются unit/component tests;
- загрузка конкретных предметных данных, auth interceptor и бизнес-формы не входят в 9.11 и начинаются с 9.12.

| 9.15  | Создание, редактирование и карточка компонента         |
| 9.16  | Галерея: загрузка, удаление и перестановка изображений |

#### 9.12 — Управление предметными областями и первый запуск

- список областей загружается через все страницы `GET /domains` с максимальным размером страницы 100 и хранится в
  TanStack Query; React context хранит только выбранный ID и производное текущее значение;
- ID последней выбранной области сохраняется в `localStorage`; после загрузки выбирается сохранённая область, а если
  она удалена или ещё не выбиралась — первая доступная;
- header содержит доступный с клавиатуры переключатель со всеми областями, текущим состоянием загрузки/ошибки и
  переходом к управлению областями; выбранный ID не добавляется в URL;
- при отсутствии областей предметные маршруты показывают first-run экран внутри обычного AppShell без обязательного
  wizard и предлагают создать пустую область или отдельно создать демонстрационную «Сборка ПК»;
- создание пустой области выполняется через `POST /domains`, создание демо — через `POST /domains/demo`; успешно
  созданная область автоматически выбирается и становится доступна всем следующим экранам;
- `/settings/domain` показывает все области, позволяет выбрать текущую, создать новую, отредактировать название и
  описание через `PUT /domains/{id}` и запросить удаление через `DELETE /domains/{id}`;
- формы используют React Hook Form и Zod: название trim, обязательно и не длиннее 255 символов, пустое описание
  отправляется как отсутствующее значение; backend field details привязываются к соответствующим полям;
- удаление всегда требует отдельного подтверждения, является безвозвратным и не скрывается как archive; существующий
  backend `409 ENTITY_HAS_RELATED_ENTITIES` отображается пользователю без попытки клиентского cascade delete;
- после удаления выбранной области выбирается первая оставшаяся, а при пустом списке приложение возвращается в
  first-run состояние; query cache всех domain-dependent функций должен использовать выбранный ID в ключе;
- loading, empty, error, create, demo, edit, switch, delete, persisted selection и mobile layout покрываются
  component tests с MSW; OpenAPI/backend/БД в 9.12 не меняются.

#### 9.13 — Управление типами компонентов и атрибутами

- `/settings/types` работает только в контексте выбранной предметной области и загружает типы через
  `GET /domains/{id}/component-types`; query key обязательно включает `domainId`;
- экран использует адаптивную master–detail компоновку: список типов и действия над ним отделены от определений
  атрибутов выбранного типа; при смене области или удалении выбранного типа выбирается первый доступный тип;
- типы сортируются по `orderIndex` (значение отсутствует — после заданных), затем по названию; пользователь может
  создать, выбрать, отредактировать или запросить безвозвратное удаление типа;
- форма типа поддерживает название, необязательные код, описание и индекс порядка; название trim/обязательно/не
  длиннее 255 символов, код не длиннее 100 символов, индекс — необязательное целое неотрицательное число;
- удаление типа требует отдельного подтверждения; backend запрещает удаление типа с компонентами или атрибутами и
  возвращает `409 ENTITY_HAS_RELATED_ENTITIES`, UI не выполняет cascade delete;
- атрибуты выбранного типа загружаются через `GET /component-types/{id}/attributes`; их query key включает и
  `domainId`, и `componentTypeId`, чтобы cache разных областей не смешивался;
- определения атрибутов сортируются по `orderIndex`, затем по label и поддерживают создание через
  `POST /component-types/{id}/attributes` и редактирование через `PUT /attributes/{id}`;
- форма атрибута содержит системное имя, пользовательский label, тип `STRING | NUMBER | BOOLEAN | ENUM`, признак
  обязательности и необязательный индекс порядка; имя и label обязательны после trim и не длиннее 255 символов;
- для `ENUM` требуется хотя бы одно непустое уникальное значение; для остальных типов `enumValues` не отправляются;
  изменение типа существующего атрибута разрешает backend только до появления сохранённых значений;
- REST endpoint удаления атрибута отсутствует, поэтому 9.13 не показывает недействующее действие удаления и не
  расширяет контракт самостоятельно;
- create/update mutations привязывают structured backend field details к форме, показывают предметные success/error
  уведомления и инвалидируют только соответствующие domain/type query keys;
- loading, empty, error, switch, create/edit type, delete/conflict и create/edit attribute включая ENUM покрываются
  component tests с MSW; OpenAPI/backend/БД/generated code в 9.13 не меняются.

#### 9.14 — Каталог: поиск, фильтры, архив, карточки и таблица

- `/components` работает только в контексте выбранной предметной области и загружает данные через
  `GET /domains/{domainId}/components`;
- поиск по названию, фильтр типа, режим активного каталога/архива и пагинация передаются в
  server query; frontend не имитирует поиск только по текущей странице;
- поиск применяется с короткой задержкой и обрезанием пробелов; любое изменение поиска, типа или
  archive-режима возвращает пагинацию на первую страницу;
- query key включает `domainId`, `componentTypeId`, строку поиска, `archived`, `page` и `size`; предыдущая страница
  сохраняется на экране во время фоновой загрузки следующей;
- типы для фильтра берутся из кэша 9.13; удалённый или не принадлежащий текущей области тип не
  сохраняется как активный фильтр;
- каталог имеет два представления над одним server state: адаптивные карточки и таблицу; выбранный
  режим сохраняется в `localStorage`;
- на телефоне таблица преобразуется в компактный вертикальный список без горизонтальной прокрутки;
- карточка показывает превью первого изображения по `orderIndex`, тип, название, бренд и ключевые атрибуты;
  при отсутствии изображения используется нейтральная заглушка, браузер получает content только через backend `/api`;
- таблица показывает название, бренд, тип, дату создания и контекстное действие; в карточках и списке
  одинаково виден общий `totalItems` и доступна одна пагинация;
- активный компонент архивируется только после подтверждения через `DELETE /components/{id}`; это обратимое действие и
  не формулируется как безвозвратное удаление;
- архивный компонент восстанавливается через `POST /components/{id}/restore`; после archive/restore инвалидируются оба
  archive-режима текущей области, а пустая после мутации страница сдвигается к предыдущей;
- переход в карточку, create/edit формы и полная галерея относятся к 9.15–9.16; 9.14 не показывает неработающих
  кнопок;
- API/query/view state, loading, initial/background error, unfiltered/filtered empty states, pagination, cards/table, mobile list,
  archive confirmation и restore покрываются unit/component tests с MSW и E2E smoke; OpenAPI/backend/БД/generated code в 9.14
  не меняются.

#### 9.15 — Создание, редактирование и карточка компонента

- каталог предоставляет заметное действие создания и открывает компонент из карточек, таблицы и мобильного списка;
  используются маршруты `/components/new`, `/components/{id}` и `/components/{id}/edit` внутри обычного AppShell;
- карточка загружается через `GET /components/{id}`, показывает название, тип, бренд, описание, состояние архива, дату
  создания, все значения атрибутов и доступные изображения только через backend `/api`; управление галереей остаётся в 9.16;
- компонент дополнительно проверяется в контексте выбранной предметной области: его тип должен входить в текущую область;
  некорректный ID, неизвестный или чужой компонент не отображается как доступный объект;
- создание выполняется через `POST /components`: пользователь выбирает тип, после чего форма загружает определения
  атрибутов этого типа; при отсутствии типов экран направляет в настройку типов и атрибутов;
- редактирование выполняется через `PUT /components/{id}` и полностью заменяет редактируемые поля и набор значений
  атрибутов; тип существующего компонента показывается, но не изменяется согласно backend-контракту;
- форма содержит обязательные тип и название, необязательные бренд и описание, а также динамические поля атрибутов,
  отсортированные по `orderIndex`, затем по label; `STRING`, `NUMBER`, `BOOLEAN` и `ENUM` получают подходящие controls;
- обязательные атрибуты валидируются до отправки; пустые необязательные атрибуты не включаются в запрос, boolean
  сериализуется как `true`/`false`, number — строковым значением без потери введённой точности;
- название обрезается по краям, обязательно и ограничено 255 символами; пустые бренд и описание не отправляются;
  structured backend field details привязываются к основным полям и динамическим атрибутам;
- успешное создание открывает карточку нового компонента, успешное редактирование возвращает в актуальную карточку;
  detail и все страницы каталога текущей области обновляются через TanStack Query cache/invalidation;
- архивный компонент доступен для чтения и восстановления, но не редактируется до восстановления; archive/restore
  используют единое подтверждение и поведение каталога без дублирования API-логики;
- уход с изменённой create/edit формы требует подтверждения, включая внутреннюю навигацию и закрытие вкладки; во время
  отправки повторное действие блокируется;
- loading/error/not-found, create, detail, edit, динамические типы атрибутов, validation, backend field errors,
  unsaved-changes guard, archive/restore и mobile layout покрываются unit/component tests с MSW и E2E smoke;
  OpenAPI/backend/БД/generated code в 9.15 не меняются.

#### 9.16 — Галерея: загрузка, удаление и перестановка изображений

- карточка компонента загружает актуальную галерею через `GET /components/{id}/images`; ошибка галереи изолирована от
  остальных данных карточки, а пустой результат отображается отдельным состоянием;
- содержимое JPEG, PNG и WebP загружается браузером только через относительные backend URL под frontend-префиксом
  `/api`, без прямого доступа к MinIO;
- активный компонент принимает по одному непустому JPEG, PNG или WebP размером до 10 MiB через
  `POST /components/{id}/images`; UI заранее проверяет доступные браузеру MIME type и размер, но backend остаётся
  источником истины для проверки сигнатуры файла;
- `orderIndex` при загрузке не передаётся, поэтому новое изображение добавляется в конец галереи; выбор файла сам по
  себе не отправляет запрос — требуется явное действие загрузки;
- изображение открывается в увеличенном доступном с клавиатуры preview; ошибка отдельного содержимого не нарушает
  управление остальной галереей;
- удаление через `DELETE /component-images/{id}` безвозвратно и выполняется только после явного подтверждения; до
  успешного ответа изображение не удаляется оптимистично, а ошибка хранилища оставляет текущее состояние на экране;
- перестановка включается отдельным режимом и выполняется доступными с клавиатуры и телефона действиями «раньше» и
  «позже» без drag-and-drop; до сохранения изменяется только локальный черновик;
- сохранение порядка одним `PUT /components/{id}/images/order` передаёт полный итоговый массив `imageIds`; отмена
  возвращает серверный порядок, а загрузка и удаление блокируются при несохранённом черновике;
- у архивного компонента галерея остаётся доступной для просмотра, но загрузка, удаление и изменение порядка скрыты;
- успешные мутации синхронизируют gallery/detail cache и инвалидируют все представления каталога только текущей
  предметной области, чтобы первое по `orderIndex` изображение оставалось актуальным превью;
- loading/error/retry/empty, file validation, upload multipart, permanent-delete confirmation, local reorder,
  atomic save/cancel, archive read-only, cache isolation, keyboard controls и mobile layout покрываются
  unit/component tests с MSW и E2E smoke; OpenAPI/backend/БД/generated code в 9.16 не меняются.

#### 9.17 — Управление ручными связями

- `/settings/compatibility/manual` работает в контексте выбранной предметной области и загружает
  `GET /domains/{id}/compatibility/graph`; ответ используется как единый источник активных компонентов (`nodes`) и
  сохранённых ручных связей (`edges`), отдельный endpoint списка не добавляется;
- query key включает `domainId`; graph-query повторно проверяется при входе на экран, чтобы после archive/restore на
  другом маршруте не показывать устаревшие компоненты, и проектируется для повторного использования в 9.18;
- экран показывает количество активных компонентов и ручных связей, локальный поиск по названию, типу, бренду и
  комментарию, desktop-таблицу и компактные мобильные карточки без горизонтальной прокрутки;
- создание выполняется через `POST /domains/{id}/compatibility` в modal-форме с двумя searchable select и
  необязательным комментарием; связь представляется как ненаправленная пара «Компонент» / «Совместим с»;
- второй список исключает выбранный компонент и уже связанные с ним компоненты; UI валидирует обязательность пары,
  self-link, известный дубль и ограничение комментария в 1000 символов, но backend остаётся источником истины для
  принадлежности области, активности и конкурентного конфликта;
- пробелы по краям комментария удаляются, пустое значение не отправляется; backend-нормализация порядка ID пары не
  меняет смысл связи, а structured field details привязываются к соответствующим полям формы;
- удаление через `DELETE /domains/{id}/compatibility/{linkId}` является физическим и безвозвратным, требует отдельного
  подтверждения с названиями обоих компонентов и не изменяет список до успешного ответа;
- успешные create/delete mutations синхронизируют и инвалидируют только graph cache текущей области, показывают
  предметное success-уведомление; ошибки используют общую нормализацию и сохраняют текущие данные на экране;
- loading/error/retry, отсутствие активных компонентов, недостаточное число компонентов, отсутствие связей, пустой
  поиск, создание, validation, duplicate conflict, delete confirm/cancel/error, domain isolation, keyboard controls и
  mobile layout покрываются unit/component tests с MSW и E2E smoke;
- автоматические атрибутивные правила не отображаются как ручные связи и остаются в 9.19; интерактивная визуализация
  тех же ручных graph edges остаётся в 9.18. OpenAPI/backend/БД/generated code в 9.17 не меняются.

#### 9.18 — Интерактивный граф совместимости

- `/settings/compatibility/graph` работает в контексте выбранной предметной области и повторно использует общий
  domain-scoped query `GET /domains/{id}/compatibility/graph`, созданный в 9.17, без дублирования server state;
- граф показывает все активные компоненты, включая изолированные, и только сохранённые ручные ненаправленные связи;
  автоматическая атрибутивная и транзитивная совместимость не дорисовывается клиентом, поскольку текущий REST API не
  предоставляет all-pairs результат для всей области;
- экран явно объясняет границы данных, показывает количество компонентов, ручных связей и изолированных компонентов,
  а также предоставляет переход к управлению ручными связями;
- компоненты отображаются custom nodes с названием, типом и брендом; типы получают стабильные theme-aware цвета и
  представлены доступной легендой, а комментарий связи показывается в панели подробностей;
- начальные координаты рассчитываются воспроизводимой force-directed раскладкой с фиксированным seed и числом шагов;
  simulation завершается до render, локальный drag не сохраняется, а действие сброса восстанавливает исходную
  раскладку;
- пользователь может масштабировать, перемещать и вписывать граф, искать компонент searchable select и центрировать
  его, выбирать узел или ребро, исследовать соседей и переходить в карточку компонента;
- выбранный узел подсвечивает соседей и incident edges, выбранное ребро — оба endpoint; остальные элементы
  приглушаются, а выбор очищается фоном или `Escape`;
- создание, переподключение и удаление связей на canvas отключены; изменение предметных данных выполняется только на
  `/settings/compatibility/manual`;
- desktop показывает canvas, minimap и боковую панель; на телефоне minimap скрывается, панель идёт после canvas, а
  поиск и список соседей остаются полноценной альтернативой пространственной навигации;
- узлы, рёбра, controls и инструкции получают локализованные ARIA labels; выбор доступен с клавиатуры, интерактивные
  цели имеют видимый focus, а цвета не являются единственным способом передать состояние;
- loading/error/retry, отсутствие компонентов, граф без связей, malformed edge, поиск и центрирование, выбор
  узла/ребра, локальный drag/reset, смена области, keyboard interaction и mobile layout покрываются unit/component
  tests и E2E smoke в Chromium, Firefox и WebKit;
- используются зафиксированные совместимые версии `@xyflow/react` и `d3-force`; OpenAPI, backend, Flyway, jOOQ и
  generated API client в 9.18 не меняются.

#### 9.19 — CRUD автоматических атрибутивных правил

- `/settings/compatibility/rules` показывает все enabled/disabled rule sets выбранной предметной области из
  `GET /domains/{id}/compatibility/rules`; query keys списка и отдельного правила включают `domainId`, а server state
  хранится только в TanStack Query;
- список показывает имя, пару типов, статус и количество AND-условий, поддерживает локальный поиск по имени/типам,
  фильтр статуса, desktop table и mobile cards; названия атрибутов разрешаются только в форме, чтобы list view не
  создавал N+1 attribute requests;
- создание и редактирование выполняются на отдельных маршрутах `/settings/compatibility/rules/new` и
  `/settings/compatibility/rules/{ruleId}/edit`; edit загружает authoritative item через
  `GET /domains/{id}/compatibility/rules/{ruleId}`;
- форма использует React Hook Form + Zod, требует имя до 255 символов, два различных типа компонентов и минимум одно
  условие; определения атрибутов загружаются существующими type-scoped queries;
- каждое условие связывает атрибут левого типа с атрибутом правого типа того же `dataType`; `EQUALS/NOT_EQUALS`
  доступны для одинаковых типов, а `GT/GTE/LT/LTE` — только для `NUMBER`; условия объединяются через AND;
- conditions добавляются, удаляются и перемещаются доступными кнопками без drag-and-drop; перед submit им назначаются
  последовательные `orderIndex` по текущему порядку, а duplicate triple attribute/operator/attribute блокируется;
- при смене типа зависимые attribute selections очищаются; backend остаётся источником истины для domain ownership,
  normalization сторон, разворота directional operator и конкурентного business-key conflict;
- create выполняется `POST /domains/{id}/compatibility/rules`, update — полным
  `PUT /domains/{id}/compatibility/rules/{ruleId}`; update заменяет все условия, поэтому UI не зависит от сохранения их
  ID или timestamps;
- quick toggle также отправляет полный PUT из authoritative rule и не меняет switch оптимистично; failed toggle/save
  сохраняет предыдущий cache/form draft;
- физическое удаление через `DELETE /domains/{id}/compatibility/rules/{ruleId}` безвозвратно, требует отдельного
  подтверждения и удаляет правило из UI только после 204;
- success mutations синхронизируют list/detail caches текущей области и затем инвалидируют только rule family этой
  области; structured backend field details привязываются к scalar и indexed condition fields;
- loading/error/retry/empty, stale IDs, search/filter, create/edit/full replacement, validation, toggle, permanent
  delete, domain isolation, unsaved guard, keyboard controls и mobile layout покрываются unit/component tests с MSW и
  E2E smoke в Chromium, Firefox и WebKit;
- preview совпадений, pagination, server search и optimistic concurrency не добавляются без отдельного backend-
  контракта; OpenAPI, backend, Flyway, jOOQ и generated API client в 9.19 не меняются.

#### 9.20 — Текущая сборка и локальное сохранение черновика

- `/configurator` заменяет placeholder самостоятельным рабочим пространством выбранной предметной области: браузер
  активных компонентов и текущая сборка находятся на одном экране;
- браузер использует пагинированный `GET /domains/{domainId}/components` с `archived=false`, server search по имени и
  фильтром типа; в 9.20 кандидаты ещё не фильтруются по совместимости;
- компоненты добавляются в любом порядке, но черновик ограничен 50 позициями и заранее допускает не более одного
  компонента каждого типа, как будущий `CreateConfigurationRequest`;
- повторное добавление уже выбранного компонента является no-op; другой компонент выбранного типа предлагается как
  подтверждаемая замена и занимает ту же позицию;
- remove изменяет только локальный черновик, а очистка всего состава требует отдельного подтверждения; backend
  mutations до 9.23 не выполняются;
- черновик автоматически сохраняется после каждого изменения отдельно для каждой предметной области в versioned
  `localStorage` record; порядок выбора сохраняется и восстанавливается после reload;
- persisted item содержит только неизменяемую пару `componentId/componentTypeId`; name, brand, images, attributes и
  archive status не дублируются и загружаются через существующий component detail query/cache;
- неизвестная, недоступная или архивная позиция не удаляется молча и не скрывает остальные элементы: UI показывает
  ID/status, retry при ошибке и явное удаление/замену;
- corrupted JSON, неизвестная storage version и недоступный `localStorage` не приводят к падению страницы; при ошибке
  записи in-memory draft продолжает работать, а пользователь получает доступное уведомление;
- desktop использует двухколоночный workspace, mobile от 360 px показывает текущую сборку перед браузером без
  горизонтальной прокрутки; все add/replace/remove/clear/retry actions доступны с клавиатуры;
- экран явно сообщает, что compatibility validation появится в 9.21, транзитивный режим — в 9.22, а серверное
  сохранение — в 9.23; текущий черновик не называется совместимой или сохранённой конфигурацией;
- storage/model, partial hydration, add/replace/remove/clear, reload, смена области, picker states, corrupted/unavailable
  storage, keyboard controls и mobile layout покрываются unit/component tests с MSW и Playwright в Chromium, Firefox
  и WebKit;
- multi-tab synchronization не входит в первый вариант; OpenAPI, backend, Flyway, jOOQ, БД и generated API client в
  9.20 не меняются.

## Демонстрационная предметная область

Пункт 9.7 добавляет атомарное создание примера «Сборка ПК» через `POST /domains/demo`. Пример содержит типы, определения
атрибутов, компоненты, ручные связи, автоматические правила и готовую конфигурацию «Игровой ПК 1440p». При ошибке
частично созданные данные не сохраняются. После создания пример автоматически открывается и дальше редактируется как
обычная предметная область. Демонстрационные изображения в первый вариант не входят; UI использует нейтральные
заглушки.

## Общие требования качества

- текущие Chrome, Edge, Firefox и Safari;
- desktop, tablet и mobile layout;
- WCAG 2.2 AA, клавиатурная навигация и видимый focus;
- loading, empty, error и success состояния для каждого server-driven экрана;
- защита от потери несохранённых изменений;
- REST DTO генерируются из `specs/configurator-api.yaml` и не дублируются вручную;
- frontend unit/component tests обязательны для каждой задачи;
- основные пользовательские пути покрываются Playwright;
- frontend lint, typecheck, tests и production build выполняются в CI;
- проект остаётся release line `0.x` до реализации runtime-аутентификации и авторизации.
